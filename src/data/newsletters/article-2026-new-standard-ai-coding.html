AI coding 最深的改變，不只是讓工程師更快寫出程式碼。當一段功能可以在幾分鐘內生成，過去圍繞「怎麼實作」建立的分工、流程與專業身分，也開始一起鬆動。此時真正稀缺的，反而變成判斷該解決什麼問題、如何驗證結果，以及最後由誰為它負責。

Raycast 在倫敦舉辦的 The New Standard，邀請 Raycast 共同創辦人兼 CEO Thomas Paul Mann、Notion AI Lead Ryan Nystrom、OpenAI Developer Relations Vaibhav Srivastav 對談，並由 Cursor 設計師 Dan Hollick 主持。這不是一場教大家使用哪套工具的發表會，而是一群身處變化第一線的產品工作者，公開討論那些還沒有標準答案的問題。

本文整理並延伸自 Raycast 的完整影片 〈The New Standard London — Raycast × Notion × OpenAI〉。

AI 寫了程式碼，人還需要讀嗎？

對談一開始便拋出最尖銳的問題：如果程式碼由 AI 產生，我們還需要閱讀它嗎？三位講者的答案並不一致，卻共同指向一件事：判斷標準不該是信仰，而是風險。

Ryan 分享，Notion 曾在兩個極端之間擺盪。一端認為 code 只是通往結果的介質，只要輸出、測試與驗證正確即可。另一端則堅持每個細節都必須由人讀過。最後他選擇中間位置：不必對每一行吹毛求疵，但必須理解系統正在做什麼，否則就無法確定究竟是人在駕馭 AI，還是 AI 在替人決定方向。所謂「讀 code」也未必是逐行閱讀，也可以是透過摘要掌握架構、資料流與改動範圍。

Vaibhav 則把標準直接連到後果。做一個自己玩的遊戲，不讀生成出的邏輯或許完全合理。但若改動的是會在大量電腦與不受信任環境中執行的關鍵基礎設施，不理解內容就不應合併。他也提到，人類審查不必孤軍奮戰：review skill、專案規則、測試與另一個 agent，都能先協助拆解大型變更，再把真正需要判斷的部分交給人。

Thomas 提供了另一種小團隊經驗。Raycast 從創業初期就不採傳統的 code review 流程，團隊直接推送、立刻在自己每天使用的產品中測試，再透過極短的回饋迴圈檢查功能與 UX。這不是「所有團隊都不需要審查」的主張，而是提醒我們：品質保證應該貼近產品風險與團隊運作方式，不必把某一套儀式當成品質本身。

不要只為今天的模型打造產品

AI 產品有一個特殊難題：開發期間模型仍在快速進步。Ryan 表示，如果只根據今天多數人負擔得起的能力設計產品，幾個月後推出時，那些能力可能已成為基本配備。Notion 因此會把模型能力與 token 價格的下降一起納入規劃，先探索今天仍昂貴、但不久後可能普及的使用方式。

不過，Thomas 認為真正的躍進通常不只來自更聰明的模型，而是模型與新互動方式的組合。ChatGPT 把模型放進對話介面，Cursor 把它帶入 IDE，後來的 coding agent 又逐漸離開編輯器、開始自行操作工具。模型沒有更換時，產品設計仍可能釋放出大量尚未被使用的能力。

這也代表 AI 產品必須懂得刪除。Dan 提到，Cursor 已開始移除半年前仍不可或缺的複雜機制，例如為了節省 context 而做的動態壓縮。當模型原生能力補上來，這些產品層的補丁反而成為負擔。好的 AI 產品不是累積最多技巧，而是知道哪些技巧已經失去存在理由。

角色正在融合，但專業沒有消失

Coding agent 也正在改變團隊形狀。Ryan 觀察到 Notion 的團隊變得更扁平，工程主管也必須更技術化。即使一個下午排滿 one-on-one，主管仍能啟動 agent 修 bug、理解架構或預先 review 變更，管理與技術工作的界線因此不再那麼清楚。

在招募上，Notion 採取近似「槓鈴」的策略：一端是能設計複雜系統、做出長期架構決策的資深人才。另一端是好奇、學得快、願意從新工具重新建立工作方式的新鮮人。被壓縮的，反而是過去只靠執行既定任務創造價值的中間地帶。

設計師也開始直接交付可執行的 prototype。Raycast 的產品設計已大量從想法直接進入產品。Notion 則建立隔離的 prototype playground，讓設計師運用真實 design system 同時做出多個版本，實際操作後再淘汰不合適的方向。OpenAI 團隊也發現，比起靜態 mockup，可互動的原型更容易讓新構想被理解與討論。

但能產出介面，不等於已經做好設計。當任何人都能快速組出一個看似完整的 app，真正拉開差距的會是對微互動、效能、轉場與細節的感受力。Thomas 更進一步提醒：工程實作本來就是解法的最後一段。如果團隊連使用者與商業問題都沒有理解，再快完成錯誤的解法也沒有價值。

速度的副作用，是思考時間被壓縮

AI coding 很容易製造一種「完成了」的錯覺。輸入 prompt、看到按鈕出現、動畫開始運作，回饋快速又令人上癮。但一天後回頭看，可能才發現自己只是沿著第一個答案不斷前進，從未停下來比較其他方向。

這是對談中最重要的反直覺觀點之一：產出成本下降，並不表示每個想法都值得被完成。Notion 曾因為實作太容易而快速做出大量點子，最後仍得停下來刪除大部分內容。AI 可以把多個方案並行做成真實原型，卻不能替團隊決定哪個問題值得長期投入。

對剛進入領域的人，Vaibhav 的建議仍是大量動手做。AI 讓初學者能以極低成本累積產品經驗，練習辨認好的互動、完成作品並真正發布。關鍵不是少做，而是從每次實作中建立判斷力，別把「生成成功」誤認為「產品成立」。

保持野心，也保持自己的方向

當 Dan 問大家會對一年前的自己說什麼，Vaibhav 的答案是更有野心：先為想做的事搭起雛形，因為模型進步的速度可能遠超想像。Ryan 則會提醒自己少看一點社群媒體。新模型、新產品與新創募資不斷出現，很容易讓團隊懷疑原本的方向、反覆轉彎，最後只剩下追逐焦慮。

Thomas 的說法更直接：沒有人真的知道答案。社群上看似篤定的預言，幾週後經常無人再提。每家公司都還在摸索。承認這一點反而能讓人重新相信自己的觀察。Dan 則提醒大家「讓身分小一點」：別過度依附設計師、工程師或經理等標籤，因為標籤會限制你去做原本以為不屬於自己的工作。

Token 用得多，不等於產出更好

面對社群上同時啟動數十個 agent 的工作流，Vaibhav 提出的不是 token maxing，而是 token minimizing：減少自己需要追蹤、審查與返工的量。他只在適合切開、能清楚驗證的任務使用 sub-agent，例如讓較便宜的模型持續關注 CI。對主要工作，少數 thread 往往已經足夠。工具不會自動放大智慧，也可能只是放大混亂。

Ryan 坦言，自己比以往更有生產力，卻也懷念過去能長時間進入 flow state 的工作方式。當人同時成為多個 agent 的協調者，注意力會被結果、追問與驗證切碎。這不是否定平行處理，而是說明新的瓶頸已從運算與打字速度，轉移到人類能管理多少條決策線。

Dan 分享 Cursor 的使用資料：token 消耗最高的 1% 使用者，使用量約是後半數使用者的 75 倍。他們較常處理 Rust、C++ 等可由測試與工具自我驗證的系統任務。這說明極高 token 使用量是一種特定工作型態，不是每位產品設計師或前端工程師都該複製的普遍標準。

最有效的 prompt 技巧，是提供真正的上下文

當觀眾追問哪些少見做法能顯著提升品質時，講者們沒有提出神奇關鍵字。Dan 會花二十分鐘寫清楚 prompt，使用精確的領域語言，並讓同一個長期對話保留專案脈絡。Thomas 與 Vaibhav 都大量使用 dictation，用幾分鐘把思路、取捨與猶豫一次說給 agent 聽，減少來回補充的輪數。

文件也有了新的讀者。Raycast 過去傾向不在 codebase 留註解，現在反而更願意留下能幫助 agent 理解背景的資訊。Notion 則把規則、不變條件與架構摘要放進 Markdown，並要求 agent 在修改程式碼時同步更新。這些文件未必是傳統教學文件，而是人與 agent 共同使用的長期記憶。

因此，真正可累積的資產不是某一版模型的 prompt hack，而是清楚的規格、可執行的測試、同步更新的文件與能檢查自身工作的 review skill。模型會更新，這些上下文仍能讓下一個模型更快進入狀況。

AI 沒有拿走 ownership，反而擴大了它

當 PR 產生速度大幅提高，責任並不會跟著交給 agent。Thomas 認為 Raycast 的 ownership 沒有本質改變，只是一個人能負責的功能與流程範圍變大。Ryan 希望 agent 接手修補小 bug 與 code gardening，但系統仍需要理解細節、能在事故發生時處理問題的人。

OpenAI 的做法則很明確：開 PR 的人仍對內容負責，不能把大量生成的變更丟給 reviewer 收拾。團隊可以用 agent 維護 runbook、補足新成員缺少的系統脈絡，但使用工具的人仍必須知道自己貢獻了什麼。AI 讓 ownership 的範圍變寬，沒有讓 ownership 消失。

個人化軟體會變多，但 SaaS 不會一夜消失

Thomas 把個人化軟體視為下一個重要方向。大眾市場的 app 必然帶有妥協。當軟體製作成本降低，每個人都可以為自己打造只服務一位使用者的小工具。它也可能從個人開始，在同事與朋友組成的微型社群中逐步擴散。Raycast 的 Glaze 正在探索這種從需求直接生成桌面 app 的路徑。

Ryan 同時補上企業軟體的現實：做出 CRM 或儀表板只是起點，部署、維護、擴充與安全才是長期成本。企業一度覺得有了 coding agent 就能取代所有既有 SaaS，最後可能發現，付費購買一套成熟產品仍比養三位工程師維護內部系統划算。未來更可能是兩者並存：成熟的垂直產品處理高可靠度需求，個人與小團隊軟體則填滿過去不值得被開發的縫隙。

能力愈高，權限愈不能預設全開

對談最後回到 guardrails 與安全。不同情境需要不同的驗收門檻：按鈕偏了幾個像素可以上線後再修，銀行系統與自動駕駛則不能用同一套「先跑再說」的標準。即使測試通過，也不代表功能適切性、整體架構與最壞情境都已被處理。

Vaibhav 特別提醒，不要習慣讓 coding agent 以 full access mode 執行。高自主性模型不應預設取得整台電腦與所有工具的控制權。可以讓 guardian model 審查 tool call、限制可操作的範圍，並從不信任的角度推演使用者可能面對的最糟結果。安全不只由模型公司負責，也同時存在於 model、agent harness 與使用者行為三個層次。

真正的新標準，是更好的掌舵能力

這場對談沒有替 AI coding 寫下一套固定流程，而這恰好是它最有價值的地方。模型與工具的變化速度，足以讓今天的最佳實務在幾個月後過時。能長期成立的，是一組更基本的原則：

  • 依照後果調整審查與驗證強度，不把讀或不讀 code 變成教條。
  • 為模型能力的進步預留空間，也持續刪掉已被模型取代的複雜機制。
  • 把快速生成用於比較更多方案，別拿它取代問題定義與思考時間。
  • 用規格、測試、文件與 skills 累積上下文，而不是追逐短命的 prompt 技巧。
  • 以完成可靠成果為目標，別把 agent 數量與 token 消耗當成生產力。
  • 讓角色邊界保持彈性，同時保留對品質、細節與系統後果的專業判斷。
  • 權限要小於能力。Agent 愈能自主行動，安全邊界就愈需要明確。

當 code 不再是最昂貴的部分，產品工作的核心會更靠近「選擇」：選擇值得解決的問題、選擇何時相信、選擇如何驗證，也選擇願意承擔哪些後果。AI 可以大幅加速航行，但方向、邊界與責任，仍是團隊真正的競爭力。
